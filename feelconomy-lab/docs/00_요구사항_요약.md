## v2로 바뀐 이유 (가장 먼저 읽어야 할 부분)

원본 요청서(§5~§11)는 "기준 데이터셋(다수 참가자) → SVD/K-means로 모델 학습 →
새 참가자를 그 모델에 투영"하는 구조였다. 이 구조에는 실행상 문제가 있었다:

> **한 사람의 감정벡터 하나만으로는 의미 있는 SVD를 할 수 없다.**
> 참가자 1명이 감정 10개를 입력하면 데이터는 `1×10` 행렬이고, rank가 최대 1이라
> 여러 잠재축을 추출하는 SVD 활동으로 적절하지 않다. 그래서 "행사 전 기준
> 데이터셋 준비"라는 선행 조건이 반드시 필요했다.

`추가 개선 내용.txt`에서 이 문제를 다음과 같이 해결하기로 했다:

> **한 참여자 × 여러 소비대안 × 여러 감성욕구 → 개인별 행렬 → SVD → 잠재요인
> → 소비대안 군집 → 현재 감정과 연결 → 개인 잠재수요**

즉 참가자 여러 명을 모아 하나의 행렬을 만드는 대신, **참가자 한 명이 자기만의
행렬 하나(소비대안 8개 × 감성욕구 6개)를 만드는 방식**으로 바꿨다. 그 결과:

- 기준 데이터셋이 더 이상 필요 없다 (실제든 합성이든)
- 사전 모델 학습·잠금·버전관리 절차가 사라진다
- 첫 번째 참가자도 자기 데이터만으로 처음부터 끝까지 계산이 끝난다
- "합성 데이터를 실제처럼 보이지 않게 표시해야 한다"는 부담(요청서 §23)도
  구조적으로 사라진다 —애초에 어떤 사전 데이터도 쓰지 않기 때문이다

원본 요청서의 §5, §6, §7(일부), §8, §9(일부), §16(모델 구축 관련)은 이 설계
변경으로 대체되었다. 아래 대응표는 그 전제 위에서 작성되었다.

## 새 계산 흐름 10줄 요약

1. 감성욕구 6축(즐거움/자극·설렘/회복·안정/소속·교류/자기표현/성취·효능감)을 config로 관리한다.
2. 소비대안 8개(식음료/카페·디저트/패션/게임/콘텐츠·구독/문화·공연/여행·체험/생활·실용)를 config로 관리한다.
3. 참가자는 현재 감성욕구 q(6개)와, 각 소비대안이 각 욕구를 얼마나 채우는지 평가한 행렬 A(8×6)를 입력한다.
4. A를 SVD로 분해한다: A = U Σ Vᵀ. 이 계산은 참가자 한 명의 데이터만으로 완결된다.
5. 참가자가 누적 설명분산 표를 보고 잠재 차원 r(2 또는 3)을 직접 고른다.
6. 소비대안 8개와 현재 욕구 q를 같은 잠재공간에 투영한다: Z = A·V_r, q* = q·V_r.
7. Z(소비대안 8개)에 k-means++를 적용해 K개 군집으로 나눈다.
8. 각 군집에는 그 군집 소비대안들의 평균 욕구 점수를 기준으로 즉석 이름을 자동으로 붙인다.
9. q*에서 각 군집 중심까지 거리를 비교해 가장 가까운 군집(잠재수요 유형)을 찾고, 그 안에서 가장 가까운 소비대안(세부 잠재수요)을 제시한다.
10. 결과는 확정 예측이 아니라 "거리가 가깝다"는 탐색적 표현으로 전달한다.

## 요구사항 대응표

### §3~§4 (v1: 감정10개+소비카테고리 설정) → v2 대응
[`src/config/needs.ts`](../src/config/needs.ts) — 감성욕구 6축. [`src/config/alternatives.ts`](../src/config/alternatives.ts) — 소비대안 8개. 둘 다 배열 하나만 수정하면 문항 수·이름·잠재공간 차원이 함께 따라간다.

### §5~§9 (v1: 기준 데이터셋/모델 학습/K-means) → v2 대응
더 이상 기준 데이터셋이 없다. 대신:
- [`runPersonalAnalysis`](../src/lib/math/inference.ts) 하나가 SVD → 투영 → K-means → 거리비교를 참가자 1명 단위로 전부 수행한다.
- [`ANALYSIS_SPEC`](../src/config/model.ts)에 r/K 기본값과 허용 범위를 설정으로 분리했다.
- 참가자가 직접 r을 고르는 것은 원본 요청서 §7("특이값 누적 설명비율을 보고 r 선택")의 취지를 그대로 살린 것이다.

### §10 (군집 결정, 표현 방식)
[`ClusterPage`](../src/pages/ClusterPage.tsx) — 제곱 유클리드 거리 최소값으로 결정하고, 화면 문구는 "현재 나의 욕구가 ○○ 군집과 **가장 가까운 것으로 나타났습니다**"이다. 1위-2위 거리 차이도 함께 보여준다.

### §11 (군집 소비특성 분석 + 이름 짓는 사람)
v1은 "연구자가 사후에 해석해서 이름을 붙인다"였다. v2는 군집이 매 참가자마다
실시간으로 새로 만들어지므로 연구자가 매번 개입할 수 없다. 그래서 이름 짓는
규칙 자체를 투명하게 코드화했다:

[`nameCluster`](../src/lib/math/clusterNaming.ts) — 군집에 속한 소비대안들의 평균 욕구 점수에서 가장 높은 1~2개 욕구의 이름을 그대로 딴다. "AI가 알아서 판단한 것"이 아니라 "내가 입력한 숫자를 요약하는 규칙"임을 [`CLUSTER_NAMING_EXPLANATION`](../src/lib/math/clusterNaming.ts)으로 결과 화면에 명시한다.

### §12 (잠재수요 표현 규칙)
[`ResultPage`](../src/pages/ResultPage.tsx) — 금지 문구("살 것입니다", "정확히 예측") 부재를 브라우저 E2E로 검증했다. 모든 문구가 "거리가 가깝다"를 주어로 삼는다.

### §15 (페이지 흐름)
[`src/App.tsx`](../src/App.tsx) 라우팅이 새 10페이지 흐름(시작→동의→욕구→**유형공개**→대안평가→SVD→지도→군집판정→결과→마무리)과 1:1 대응한다. 진행률은 `1/7`~`7/7`으로 표시된다 (시작·동의·마무리는 진행률에서 제외). 유형공개(`/type`) 페이지는 v3에서 추가되었다 — 자세한 내용은 [`05_필코노미_유형표.md`](05_필코노미_유형표.md).

### §16 (관리자 페이지)
v1의 4탭(데이터셋/모델구축/군집분석/참가자)이 2탭으로 줄었다 — [`AdminSpecTab`](../src/pages/admin/AdminSpecTab.tsx)(설정 확인, 실행 없음. v3부터 필코노미 유형표도 함께 표시), [`AdminParticipantsTab`](../src/pages/admin/AdminParticipantsTab.tsx)(조회·CSV 내보내기. v3부터 유형 코드 열 포함). 학습·잠금 절차가 없어졌기 때문이다.

### §17~§18 (데이터 저장, 개인정보)
[`ParticipantRecord`](../src/lib/types.ts) — 입력 원자료(q, A), 분석 규격 버전, 잠재좌표, 배정 군집, 세부 잠재수요를 모두 저장한다. 이름·전화번호·이메일·학번 입력 필드는 코드에 존재하지 않는다. 익명 ID `P-YYYYMMDD-NNN` 형식은 v1과 동일하다.

### §19~§20 (기술 스택, storage 분리)
TypeScript + React + Tailwind CSS. 수학 모듈(`src/lib/math/`)은 UI를 import하지 않는다. [`ParticipantRepository`](../src/lib/storage/repositories.ts) 인터페이스 + localStorage 구현으로, 중앙 DB 교체가 한 파일 수정으로 가능하다. (v1에 있던 ReferenceDatasetRepository/ModelRepository는 대상이 사라져 함께 제거했다.)

### §21~§22 (디자인, 접근성)
어두운 배경 + 그라디언트 메쉬 + 유리질감 카드로 리프레시했다. 화면 제목 아래 소제목을 두지 않고, 설명은 본문 흐름에 자연스럽게 배치했다. 학교 로고를 헤더·시작화면·푸터에 통합했다. 접근성 요소(포커스 표시, `role=radiogroup`, `aria-label`, 색상 외 구분)는 v1과 동일하게 유지했다.

### §23 (금지사항) — v2에서의 재해석
| 원본 금지 항목 | v2에서의 상태 |
|---|---|
| 1. 실제 감정 데이터 생성 | 해당 없음 — 어떤 사전 데이터도 생성하지 않는다 |

| 4. 군집 이름 확정 | 군집 이름은 매 참가자마다 규칙 기반으로 즉석 생성되며, 그 규칙을 화면에 공개한다 |
| 5. 실제 소비확률 생성 | "확률"이라 부르지 않고 "거리"로 표현한다 |
| 7. 기준 데이터 없이 결과 출력 | 해당 없음 — 참가자 자신의 입력이 유일한 데이터다 |
| 8. 참가자마다 자동 재학습 | 해당 없음 —애초에 "학습"이라는 절차가 없다 |
| 9. 확정적 예측 표현 | 금지 문구 부재를 E2E로 검증 |
| 10. 불필요한 개인정보 수집 | 해당 입력 필드 없음 |

### §26 (코드 품질)
